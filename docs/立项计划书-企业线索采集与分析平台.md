## 1. 项目背景与建设动因

企业在抖音企业号线索版等后台（如 `https://leads.cluerich.com/`）存在**每日线索、互动记录、内容（视频）相关数据**的经营分析需求。数据分散在 Web 后台与员工本地 Excel 中，缺乏统一的**采集、合并、脱敏上云与全员分析**能力。

本项目建设一套以 **Playwright 本机采集** 为核心、**Web 控制台远程编排**、**PostgreSQL 承载分析数据**与 **Web 侧栏「数据大盘」等经营看板** 的软件体系，并在**多租户 / 多部门**场景下满足**最小上云（脱敏后）**的安全与合规目标；**敏感计算与原文处理一律在绑定客户端执行**（见第 4.2 节）。

---

## 2. 建设目标（SMART 方向，待评审量化）

1. **采集自动化**：员工本机客户端可稳定执行后台导航与数据采集（含分页、Tab、详情等复杂交互），支持按任务/定时策略运行；**具体采集逻辑以可配置的「自动化规则」为准**（见第 4.1 节），而非仅依赖客户端硬编码。
2. **多源合并**：支持将 Playwright 抓取结果与本地 **Excel** 解析结果在客户端侧合并为统一业务口径。
3. **脱敏上云**：仅将经确认的**脱敏/假名化**数据同步至云端 PostgreSQL，供 BI 或 Web 看板使用；敏感原始数据默认保留在客户端可控存储内（策略待最终确认）。
4. **远程控制**：Web 端可绑定设备、下发任务、查看任务状态与**非敏感**运行摘要；客户端通过出站长连接（如 WSS）对接，适配常见办公网络环境。
5. **版本与口径一致**：通过**启动更新 + 服务端最低版本闸门**降低「各台电脑处理逻辑不一致」带来的数据漂移风险。
6. **多租户多部门**：租户、部门、账号权限在云端统一配置；上传与查询均带租户上下文，避免串数据。
7. **「自动化规则」菜单**：Web 控制台侧栏/导航中的**中文菜单名固定为「自动化规则」**（与「数据大盘」「员工账号管理」「线索管理」「视频管理」「推荐视频」并列；不使用「采集规则」等其他叫法）；该菜单内支持规则的增删改查、版本/发布、**下发至已绑定客户端**（随任务或策略同步）；客户端按规则执行（如：菜单路径、筛选项「最近互动时间」日期范围、Tab「未留资/已留资」、翻页策略等，字段以详细设计为准）。**规则编辑的单一事实来源在 Web**；客户端提供同名或等价入口的**使用引导与只读状态**（见第 4.3 节），避免双端各维护一套编辑器导致口径漂移。
8. **Web「数据大盘」菜单**：Web 控制台侧栏/导航中的**中文菜单名固定为「数据大盘」**（与「员工账号管理」「自动化规则」「线索管理」「视频管理」「推荐视频」并列；页内能力可对齐抖音后台「数据分析」类能力，**侧栏展示名**不改为「数据分析」等替代词）；在 Web 端提供经营看板（示意：日期范围、**按账户切换/筛选**、线索类 KPI 与趋势、**短视频/视频列表与明细**等模块）；展示数据以**已上云的脱敏/聚合结果**为准，**不在云端直接驱动 Playwright**（见第 4.2 节）。
9. **执行落点统一（绑定客户端）**：无论数据来自 **浏览器抓取** 还是 **Excel**，无论操作入口在 **Web** 还是 **Electron 客户端**，**解析、合并、脱敏及上传前处理**均必须在**与该用户/组织绑定的客户端设备**上执行，以保证敏感原文与解析逻辑不脱离受控终端（路由与实现细节见第 4.2 节）。
10. **Web「员工账号管理」菜单与业务双轨**：Web 控制台侧栏/导航中的**中文菜单名固定为「员工账号管理」**（与「数据大盘」「自动化规则」「线索管理」「视频管理」「推荐视频」并列）。菜单内对抖音矩阵/经营场景下的**采集与授权对象**分轨管理：**企业员工号**（企业开通/分配的企业号体系）与 **员工个人号授权**（员工个人抖音号经企业授权接入）；与部门、岗位、授权/过期状态、撤销等字段对齐（见第 6.2 节），并与任务中的 **`account_id` / 登录态** 绑定一致。
11. **Web「线索管理」菜单**：Web 控制台侧栏/导航中的**中文菜单名固定为「线索管理」**（与「数据大盘」「员工账号管理」「自动化规则」「视频管理」「推荐视频」命名策略一致，不使用「高潜用户」等后台子页面名替代侧栏名）；提供对标抖音企业号线索后台「**用户数据概览 + 筛选 + 核心用户列表**」的经营操作视图；支持按 **负责员工/操作人**、**时间范围**、**抖音账户（`account_id` / 抖音号）** 等多维筛选查看线索；列表与 KPI 数据来自 **PostgreSQL**（客户端同步后的脱敏/可展示数据），**不在 Web 内嵌 Playwright 直连** [抖音企业号商家管理后台](https://leads.cluerich.com/) 实时抓数（见第 4.4 节）。
12. **Web「视频管理」菜单**：Web 控制台侧栏/导航中文名固定为 **「视频管理」**（与「数据大盘」「员工账号管理」「自动化规则」「线索管理」「推荐视频」并列）；展示与本租户 **§6.2 绑定关联的抖音业务账户** 下的**短视频/视频清单与指标**（播放、完播、线索量、发布时间等，以可采集字段为准）；支持 **单抖音账户** 查看其下全部视频，及 **当前平台用户权限范围内全部抖音账户** 聚合查看；提供 **排序/筛选**（如 **播放量最高**、**发布时间最新** 等）与 **账号/部门/时间** 等筛选；数据来自 **PG**，刷新依赖客户端同步（见第 4.5 节）。
13. **Web「推荐视频」菜单（独立侧栏，与视频管理联动）**：Web 控制台侧栏为**独立顶层菜单项**，中文名固定为 **「推荐视频」**（与「数据大盘」「员工账号管理」「自动化规则」「线索管理」「视频管理」并列；**不**嵌入「视频管理」内作为子 Tab）；在 **RBAC 范围内全部抖音业务账户** 的已同步视频中，基于 **点赞、评论、收藏、转发** 等综合指标与**可配置/可版本化的计算公式**产出 **优质度/推荐排序**，以卡片或榜单形式帮助管理员**快速识别值得投放广告（如 Dou+）与重点运营**的视频；与 **「视频管理」同源视频实体与指标**，提供**交叉跳转与筛选条件联动**；**首期**以展示、排序、导出与运营备注为主，**批量投 Dou+ 等广告投放 API 对接**作为可选后续迭代（见第 4.6 节）。
14. **Web「设备绑定」与「系统设置」侧栏（一级，已冻结）**：在 **§3.3.2** 所列**经营类**（含**「投放管理」** 等，见该节表格）之后，**自上而下**为两项**控制面**一级菜单：**「设备绑定」**（独占绑定码、设备列表、`device_id` 与在线/WSS 会话摘要、解绑与审计等**设备生命周期**能力，**不**与任务编排、组织人员维护混为同一菜单）；**「系统设置」**（承载租户内 **组织与成员**、**平台用户**与 **RBAC**、**任务中心**（编排、执行历史、与任务相关的客户端状态摘要）等，**不含**设备列表主流程——设备见 **「设备绑定」**）。两项中文名与路由为产品/工程**单一事实来源**，与附录、§3.1 一致。

### 3.3 信息架构（IA）：Web 控制台导航与页面层级

本节定义 **Web 控制台** 的**一级侧栏顺序**（**前六项经营类** + **「投放管理」** + **「设备绑定」「系统设置」** 控制面等，见下表；**共九项**一级侧栏名）、**主要二级页面/Tab** 及 **「设备绑定 / 系统设置」边界**，作为产品原型与前端路由的**单一事实来源**（与 §3.1、附录「侧栏菜单中文名」一致；若与早期「仅八项」表述冲突，以 **本节表格** 与 [**`数据字典-视频投放-示意.md` §6.1**](数据字典-视频投放-示意.md) 为准）。

#### 3.3.1 设计原则

- **租户上下文优先**：进入任一业务菜单前须已选择 **「当前租户」**（见 §6.1）；侧栏与路由均在该租户域内解析。  
- **RBAC 驱动可见性**：一级/二级菜单项按角色隐藏或禁用；**数据类菜单**另受 **行级/列级** 数据范围约束（见 §6.1）。  
- **命名冻结**：**前六项经营类、第七项「投放管理」、以及「设备绑定」「系统设置」** 的侧栏中文名已冻结（详见 §3.3.2）。**不**因抖音后台改版而改上述侧栏文案；页内 Tab 可与抖音对齐但须在帮助文档中中英对照。  
- **与客户端协同**：Electron **「打开 xxx」** 与 Web **路由 path** 一一映射（见 §3.3.5）。

#### 3.3.4 「设备绑定」与「系统设置」的边界（已定）

- **「设备绑定」**（侧栏一级，中文名已冻结）：独占 **设备注册/解绑与连接面**（绑定码、设备列表、`device_id`、在线或 WSS 摘要、解绑审计）。**不把**任务编排、部门/人员主数据维护作为主入口放在本菜单，以免与「自动化规则」「员工账号管理」等经营菜单职责交叉混乱。  
- **「系统设置」**（侧栏一级，中文名已冻结）：承载 **组织与成员**、**平台用户**与 **RBAC**、**任务中心**（任务编排、执行历史、与任务相关的客户端/WSS 状态摘要）等。**不含**设备列表与绑定码主流程（见 **「设备绑定」**）。  
- **顶栏补充**：**「当前租户」** 切换仍可保留在顶栏；与 **「系统设置」** 内组织信息展示须上下文一致。  

**原则**：避免再增加与**既有经营类**菜单**易混淆**的侧栏一级名（如不再单开一级「数据分析」替代「数据大盘」）；**「投放管理」** 已在 [数据字典-视频投放-示意.md §6.1](数据字典-视频投放-示意.md) 定稿，与**按视频、人填投放/投前**（`biz_ad_placement`）一一对应，不与其他菜单合并。

| 线索管理 | `/t/:tenantId/leads` | 可带筛选 query |
| 视频管理 | `/t/:tenantId/videos` | 可带 `accountId` |
| 推荐视频 | `/t/:tenantId/recommended-videos` | 与视频管理互跳带 query |
| 投放管理 | `/t/:tenantId/ad-placements` | 与**视频/推荐**可互链；**须**带 `tenantId` 深链；字段见 [数据字典-视频投放-示意.md](数据字典-视频投放-示意.md) |
| 设备绑定 | `/t/:tenantId/device-binding` | 可与「复制绑定码 / 唤起客户端」按钮同页；深链须带 `tenantId` |
| 系统设置 | `/t/:tenantId/system-settings` | 可子路由如 `.../organization`、`.../tasks`；实现以工程为准 |

**安全**：深链须校验 **租户 + RBAC**；禁止仅靠 query 切换租户。

## 4. 总体架构（逻辑）

```
[员工本机 · 绑定客户端]
  Electron（托盘/绑定码/状态/日志/启动更新）
        │
  本地执行核心：更新器 │ Playwright（建议子进程）│ Excel 解析 │ 合并 │ 脱敏
        │         ▲                              │
        │         │  抓取 / Excel 均在此处理      │
        └──────── WSS（出站，绑定后）───┼──► [云端] Web 控制台 + API +「数据大盘」等
                                       │         （仅编排/查询；敏感执行不下云）
                                       └──► PostgreSQL（脱敏明细/汇总）
                                                └──► Web「数据大盘」/ BI / 只读分析
```

**原则**：控制指令与元数据走云端；**重数据处理与敏感原文**默认在**绑定客户端**完成后再选择性上云；**「数据大盘」**等 Web 能力**只读**已入库的可展示数据。

### 4.1 业务需求补充：「自动化规则」菜单与规则内容（必须作为规则实现 + Web 维护与下发）

**背景（已确认的产品方向）**：例如抖音企业号线索后台「用户管理 → 高潜用户」场景中，需支持按 **「最近互动时间」等指定日期范围**、**「未留资 / 已留资」Tab** 等条件抓取数据；此类逻辑应沉淀为**自动化规则**，由运营/管理员在 Web 维护，并**下发到客户端**执行，避免仅能通过发版改脚本。

**Web 端能力（菜单级）**

- **菜单中文名**：**「自动化规则」**（Web 控制台侧栏/导航固定；与「数据大盘」「员工账号管理」「线索管理」「视频管理」「推荐视频」并列，全站统一）；功能包括：列表、创建/编辑、复制、启用/停用、**版本号或发布态**（草稿/已发布）。
- **规则内容**：至少覆盖「入口路径 / 筛选参数（含日期范围占位符，如任务入参覆盖）/ Tab 与列表行为 / 可选：网络监听优先或 DOM 策略」等（**具体 JSON Schema 或 DSL 在详细设计中定稿**）。
- **下发**：将**已发布规则**推送到指定租户下的设备（或设备组）；客户端在连接后**拉取或随 WSS 推送**规则增量；任务执行时携带 `rule_id` + 运行时参数（如 `start_date`、`end_date`、目标账号绑定）。
- **审计**：谁在何时修改、发布了哪条规则；哪台设备在何时使用了哪一版规则执行任务。

**客户端职责**

- 内置**规则解释器 / 执行器**（与 Playwright 子进程协作）：校验规则与当前**客户端最低兼容版本**；不兼容则拒绝执行并上报明确错误码。
- 规则与**多账号 storageState** 解耦：任务层指定账号，规则层描述页面行为。

**与「启动更新」的关系**

- 规则适合承载**频繁变更的页面步骤与参数**；**执行器内核**仍在客户端程序内，通过 **Electron 更新**保障安全与能力边界；二者通过 **规则 schema 版本**协商兼容。

#### 4.1.1 规则如何驱动 Playwright、如何创建规则、管理员如何调试（技术草案）

**核心概念：Playwright 不直接「读懂」自然语言**  
客户端内实现 **规则解释器（Rule Runner）**：把 Web 下发的一条规则（建议为 **带 schema 版本的 JSON**，或受控 **DSL**，禁止任意脚本）翻译成对 Playwright API 的调用序列（`goto` / `click` / `fill` / `locator` / `waitForResponse` 等）。**任务参数**（如 `start_date`、`end_date`、留资 Tab 枚举）在运行时注入，替换规则中的占位符。

**管理员 / 实施人员「创建规则」的可行路径（可组合，详细设计时选一主路径）**

| 方式 | 做法 | 适用 |
|------|------|------|
| **A. 模板 + 参数化（推荐作基线）** | 研发预置「高潜用户列表」「数据分析概览」等**官方规则模板**；管理员在「自动化规则」里只做**启用、复制、改参数映射**（日期字段、Tab、账户维度），不改底层选择器。 | 后台改版由研发发版更新模板 + 客户端兼容版本；管理员低门槛。 |
| **B. 可视化编排器** | 将步骤抽象为积木：`导航`、`设日期范围`、`点 Tab`、`翻页`、`抽取表格`、`监听接口` 等；管理员拖拽生成 JSON。 | 需要投入编辑器开发；仍受积木能力边界约束。 |
| **C. 录制 / Codegen 辅助** | 在**受控环境**（绑定客户端或专用调试机）用 Playwright **Codegen / 自研录制**生成步骤草稿 → 导入为规则 JSON → 管理员在 Web 中补全元数据、参数占位符后发布。 | 降低「从零写选择器」成本；产出需人工审核与脱敏后再下发。 |
| **D. 仅研发维护 JSON** | 管理员无编辑器，仅选规则包版本；适合极早期。 | 迭代慢，不适合频繁改筛选。 |

**「线索按日期 + Tab」在规则里长什么样（示意，非最终实现）**  
用声明式步骤描述业务，而非把整段 TS 存进库。例如：`steps: [ { "type": "goto", "path": "/pc/user-manage/high-dive-user/list" }, { "type": "setDateRange", "field": "最近互动时间", "start": "{{start_date}}", "end": "{{end_date}}" }, { "type": "clickTab", "name": "{{lead_tab}}" }, { "type": "collectTable", "mode": "paginate" } ]` —— 具体字段名、选择器策略（`getByRole` / `data-testid` / 降级链）在 **schema 与 Runner 实现**中统一，避免管理员手写脆弱 CSS。

**数据抽取两条通道（与 Runner 并列）**  
- **DOM 通道**：按规则操作表格行。  
- **网络通道**：规则声明 `captureResponses`（URL 模式或标记）；Runner 在 Playwright 中 `page.on('response')` 解析 JSON，往往比纯点日历更稳；**管理员调试时可对比两路结果**。

**管理员如何调试规则（建议纳入产品能力）**

1. **在本机「试跑」**：Web 对某设备下发 **「调试执行」**（仅管理员角色）： headed 浏览器、可放慢、**单次不写入生产上报**或写入沙箱数据集（待决）。  
2. **Playwright Trace**：**生产 Runner 默认关闭**（见 **§5.3**）；在试跑/排障等按需开启时，可在失败或试跑结束时生成 **trace.zip**（默认仅存**本机**或按策略脱敏后上传片段）；管理员用 **Playwright Trace Viewer** 逐步查看 DOM、网络、截图。  
3. **日志与步骤序号**：Runner 每步打 `step_id` 与耗时；错误回传 `failed_step` + **非敏感**错误摘要。  
4. **规则版本对比**：Web 展示 JSON diff，便于回归。  
5. **环境与账号**：调试使用**测试/沙箱账号**或脱敏副本（若平台无沙箱，则明确仅用副本数据、限制人员）。  

**与安全的边界**  
调试产物可能含敏感信息，须遵守第 6 节：**默认本机保留**、下载/上传需权限与审计；禁止把含明文 PII 的 trace 无差别同步到公有云。

**研发侧参考：Playwright 官方运行与 UI 调试（与产品「管理员试跑」的关系）**

- Playwright 文档 [Running and debugging tests](https://playwright.dev/docs/running-tests) 说明如何通过命令行运行用例、使用 **`npx playwright test --ui` 进入 UI Mode**、以及 `--headed`、`--debug`（Playwright Inspector）等调试手段。  
- [UI Mode](https://playwright.dev/docs/test-ui-mode) 进一步说明时间线、Actions、Network、**Pick locator**、DOM 快照弹出等能力，适合**研发人员在代码仓库内**维护 **Rule Runner、官方规则模板或 `@playwright/test` 回归用例**时做逐步调试与定位器选取。  
- **与产品的分界**：上述 UI Mode 面向 **Playwright Test 工程**；交付给客户的 Electron 客户端**不要求**安装 `playwright test` CLI。产品上管理员的「规则试跑 / Trace 查看」宜实现为：**在绑定客户端上由 Runner 开启 `trace`、有头模式等**（能力对齐官方思路），或允许**经授权的研发本机**用同一套官方工具对模板用例调试后再发布规则；二者在权限与数据出境策略上分开治理。

- **是否必须单独做一套「控制端」软件来调试再上传？**（结论）**不必然。**
  - **发布/下发**已在架构中由 **Web「自动化规则」+ 云端存储 + 对客户端 WSS/拉取** 承担，**不需要**为此再专门做一个与 Web 平行的「上传器」；管理员/实施在 Web 内完成「保存草稿 → 发布 → 指定租户/设备下发」即可。  
  - **调试 Playwright/规则**有两种常见落法，可分期：  
    - **MVP/研发向**：在代码仓库用官方 **`playwright test` / UI Mode**（见上节链接）调试 **规则模板与 Runner**；定稿的 JSON/DSL 经 **内管或 Web 表单项** 录入发布——**不强制**再开发一个独立「调试台安装包」。  
    - **产品化/可选**：若需让**非研发**（或驻场）在受控环境下调规则，可迭代 **（a）** Web 内对**某台已绑定设备**发「试跑（有头+trace）」、结果回传摘要；**（b）** 或**内部专用**小工具/与生产同内核的 Electron 调试包——与**生产客户端**可复用子进程，避免两套 Runner。  
  - **避免**：再做一个与 Web、与生产客户端都割裂的第三套「控制端」却不同步规则 schema，除非明确为**仅内网**工具并规定与主线的同步流程。

### 4.2 业务需求补充：Web「数据大盘」菜单与「绑定客户端执行」原则

**菜单中文名**  
Web 控制台侧栏/导航中固定为 **「数据大盘」**（与「员工账号管理」「自动化规则」「线索管理」「视频管理」「推荐视频」并列；**不**将侧栏名改为后台常用词「数据分析」整体替代，以免与能力描述混淆）。

**数据大盘（页内能力参考后台「数据分析」）**

- **「数据大盘」**菜单内支持 **日期范围**、**按企业号/账户维度**筛选或切换（与后台「账户选择」类似，映射为系统内 `account_id`）；展示 **每个账户的线索数据**（次数、趋势、转化相关指标等，以可获取字段为准）、**抖音短视频/视频列表与详细数据**（播放、曝光、互动等，以可获取字段为准），以及内容营销/服务转化等模块的**可上云指标**（分阶段迭代）。
- 大盘图表与表格的数据来源：**PostgreSQL**（及汇总物化视图/API），**不**在浏览器云端直接打开抖音后台抓取。

**数据来源：抓取与 Excel 两条路**

- **浏览器抓取**：由绑定客户端按自动化规则与任务参数执行 Playwright，结果在客户端合并、脱敏后上报。  
- **Excel 补充/导入**：业务上允许通过 Web 或客户端发起「导入」动作，但 **Excel 的解析、校验、与抓取结果的合并**须在**同一绑定客户端**完成后再上报脱敏结果（见下条「执行落点」）。

**执行落点（安全原则，已确认方向）**

- 定义：**绑定客户端** = 与某 Web 用户或某组织内责任主体完成设备绑定、且被任务/策略指定为 **唯一执行终端** 的 Electron 实例。  
- **强制**：凡涉及 **Excel 原文、后台页面 DOM/接口原文、未脱敏 PII** 的处理，**仅**允许在该绑定客户端进程内执行；云端仅接收**已脱敏或可展示粒度**的结构化数据及任务元数据。  
- **可上云字段清单**：以 **`docs/脱敏白名单-上云字段.md`** 为**单一事实来源（骨架）**；研发通过 **Playwright / 网络监听** 确定解析路径后回填该表，经产品/安全定级（L0–L3）后，客户端 Runner **出口闸门**仅允许上报白名单内字段。  
- **Web 发起操作**：用户在 Web 点击「同步数据」「导入 Excel」等 → 服务端将指令排入 **目标绑定客户端** 队列 → 经 WSS 下发 → **客户端执行**；Web 仅展示进度与结果摘要。  
- **客户端发起操作**：用户在 Electron 内触发同类任务 → 仍在**本机**执行，上报逻辑一致。  
- **用户—设备映射**：须在产品上定义（示例：一名员工默认绑定一台办公电脑；或「账户 A 的数据仅允许由设备 D1 回写」）。**未在线的绑定客户端**无法接受执行时，Web 应明确提示「需客户端在线」，避免退化为云端解析 Excel。

**Web 端「上传 Excel」的实现路径（详细设计中必选其一或组合）**

- **推荐优先**：Web 仅发起任务 → **客户端弹出本地文件选择器**读取 Excel → 本地解析（原文不出终端）。  
- **备选**：经安全评审后，采用**端到端加密**的临时投递（短 TTL）由客户端拉取并本地解密解析，云端不持久存明文。  

### 4.3 客户端侧客户使用路径与「自动化规则」入口（必须有，但与 Web 分工不同）

**为何客户/员工必须安装客户端**

- 没有本机 **Electron + Playwright**，就无法在**绑定终端**上完成浏览器抓取、Excel 原文解析与脱敏前合并，Web 与云端**不能替代**该执行面（见第 4.2 节）。因此**客户侧日常使用＝「装客户端 + 浏览器打开 Web」的组合**，其中客户端是**必装**组件。

**客户端必须具备的「会用」能力（产品级，建议纳入 MVP）**

1. **首次引导向导**：安装 → 启动更新 → 展示/输入 **绑定码** → 连接成功提示 → 引导 **登录抖音企业号后台一次**（生成/更新 `storageState`）→「自检通过」再进入托盘常驻。  
2. **托盘 + 主窗口**：常驻显示 **在线/离线**、**当前租户/设备名**、**最近同步时间**、失败时**错误摘要（非敏感）**；支持 **「立即执行队列中的任务」**（可选）与 **打开日志目录**。  
3. **与 Web 的衔接（降低学习成本）**  
   - 提供 **「打开数据大盘」**、**「打开员工账号管理」**、**「打开线索管理」**、**「打开视频管理」**、**「打开推荐视频」**、**「打开投放管理」**、**「打开自动化规则」**、**「打开设备绑定」**、**「打开系统设置」** 等按钮：**优先使用系统默认浏览器**打开已配置的 Web 控制台 URL（可带租户上下文或 deep link 路由），避免在 Electron 内嵌复杂登录态与 Cookie 隔离问题。  
   - 可选：在客户端内嵌 **WebView** 加载自家控制台（需单独评估 SSO、Cookie、安全边界）；**不推荐**在客户端再实现一套与 Web 完全重复的「自动化规则」可视化编辑器。  
4. **「自动化规则」在客户端呈现方式（推荐）**  
   - **菜单/设置项中文名仍可为「自动化规则」**，但内容为：**已下发规则列表（只读）**（规则名、`rule_id`、版本、最近同步时间、是否兼容本客户端）；附 **「在网页中编辑」** 跳转至 Web 侧 **「自动化规则」** 菜单。  
   - 这样客户**既在客户端「看得见规则」**，又不会维护两套编辑逻辑；与第 2 条建设目标「单一事实来源在 Web」一致。  
5. **采纳体验增强（可选迭代）**  
   - **Deep link**：`自定义协议://bind?code=xxxx` 从 Web 点击「打开客户端绑定」唤起 Electron 并自动填入绑定码。  
   - **企业 IT 静默安装/预置服务端地址**，减少员工配置成本。

**小结**

- **客户端要有**：是，且是**主入口之一**（装软件、保在线、保登录态、看状态、触发本机执行）。  
- **「自动化规则」是否要在客户端再做一套完整菜单**：**不建议**；更好是 **同名入口 + 只读同步状态 + 跳转 Web 编辑**。**「数据大盘」「员工账号管理」「线索管理」「视频管理」「推荐视频」「投放管理」「设备绑定」「系统设置」** 以 **Web 展示/编排**为主，客户端通过按钮一键跳转至 Web 侧栏**已冻结中文名**的对应菜单即可（「投放管理」为 Web 人填/记账主场景，**客户端可选**不单独做入口或仅做「打开广告/投放管理页」深链，与 §3.3.2 一致即可）。

### 4.4 业务需求补充：Web「线索管理」菜单（列表 + 概览 + 多维筛选）

**菜单中文名**

| 客户端形态 | **已决：Electron** | 安装包分发；本地负责绑定、状态、更新与执行器编排；复杂配置与全员看板在 Web |

### 5.1 客户端形态与 Web 远程控制（已决方案说明）

**客户端：Electron**

- 交付形态为 **Windows/macOS 安装包**（具体平台以评审为准），内置自动更新（如 `electron-updater` 等，实现选型在详细设计中确定）。
- Electron 主界面承担：**本机绑定**（展示绑定码/扫码）、**首次引导**、**连接与版本状态**、**当前任务摘要（非敏感）**、**日志入口**、**打开 Web（「数据大盘」「员工账号管理」「线索管理」「视频管理」「推荐视频」「投放管理」「自动化规则」「设备绑定」「系统设置」等）**、**已下发规则只读列表**、**手动重试/暂停（可选）**；复杂任务编排、历史查询、租户管理、规则**编辑**在 **Web 控制台**（见第 4.3 节）；Web 侧 **「设备绑定」** 菜单与客户端本机能力互补（管理员视角设备列表与审计以 Web 为准）。
- **Playwright 建议放在子进程**中执行（与 Electron 内嵌 Chromium解耦），便于崩溃隔离、资源回收与独立日志。

**Web 在绑定后如何「控制」客户端**

1. **绑定（一次性或换机时）**：Web 生成绑定码 → 用户在 Electron 内输入/扫码 → 客户端携带绑定凭证向云端注册，获得 **设备级长期令牌** 与 **租户/部门上下文**。
2. **长连接**：Electron 启动后（或绑定成功后）建立 **出站 WSS**，保持在线心跳；断线自动重连。
3. **控制流**：管理员/授权用户在 Web 上对该设备下发指令（如「执行某日线索同步」「**同步自动化规则**」「更新策略包」「取消任务」）→ **服务端仅通过该设备已建立的 WSS 会话**将指令推给对应客户端（或客户端轮询拉取，备选）；客户端执行后回传**结构化状态**（进度、错误码、条数等，不含敏感原文）。任务体应引用 **`rule_id` + 运行时参数**（如日期范围）。
4. **安全**：指令需鉴权（谁有权控哪台设备、哪租户）；敏感操作可要求二次确认或角色约束；全程 TLS。

**原则不变**：控制与元数据在云端编排；**采集浏览器与敏感原文处理**在员工本机；上云数据仍遵循脱敏策略。

### 5.2 客户端多系统/多版本支持（结论）

- **可以**同时支持**多套操作系统**（常见组合：**Windows + macOS** 双端各一份安装包），**同一代码基**以 Electron 跨平台方式构建；**不是**一个 `.exe` 在 macOS 上直接运行。Linux 若需要可再单列，看客户环境（非默认）。  
- **同一系统内的多个版本**（如 Windows 10 与 11、macOS 12/13/14/15）通常**一套安装包在不低于「最低支持版本」的机器上均可安装**，但须在文档中写明 **「最低：Windows 10 某构建 / macOS 某大版本起」**——下限由所用 **Electron 大版本**、其内置 **Chromium** 的各平台支持范围（以 [Electron 文档/发行说明](https://www.electronjs.org/docs/latest/) 与所选版本为准）及 Playwright 对浏览器二进制的支持共同决定，**每升级 Electron 主版本需复核**。  
- **Playwright 浏览器**：在各 OS 上分别下载对应浏览器缓存（体积大），**首次安装/更新**需随客户端打包策略说明磁盘与网络。  
- **与「多账号」无冲突**：**多系统**指 OS 种类/版本；**多账号**仍指各 `storageState` 与业务账号隔离，与 OS 无直接关系。  
- **工程上**：发布流水线分别产出 `win` / `mac` artifact；**CI** 至少在最低档目标系统或虚拟机做一次冒烟（安装、启动、绑定、跑一条空规则）。

### 5.3 Playwright 绑定与运行时约定（已决）

1. **语言绑定**：客户端 **Rule Runner** 使用 Playwright 官方 **Node / TypeScript** API（与 Electron **同栈**），与仓库 [microsoft/playwright](https://github.com/microsoft/playwright) 文档一致；**生产路径不采用** [microsoft/playwright-python](https://github.com/microsoft/playwright-python)。  
2. **并发约束**：产品与工程上限制 **并行任务数** 与 **同时存活的 `BrowserContext` 数量**（具体上限在详细设计与压测中给出），避免员工本机因多实例 Chromium **内存/CPU** 被拖垮。  
3. **复用 `BrowserContext`**：在同一会话或同批采集内 **优先复用** `BrowserContext`（及合理的 `Page` 生命周期），**避免**无必要地反复全量 `browser.launch`；**多抖音业务账号**仍须以 **独立 `storageState` / 独立 Context** 隔离，不得为省资源串号。  
4. **Trace 默认关闭**：生产 Runner **默认不开启** Playwright Trace；仅在 **管理员试跑、故障诊断、经授权支持** 等场景 **按需开启**，并遵守 **磁盘占用、本机保留与脱敏** 策略（与 §4.1.1 衔接）。  
5. **`headless` 默认、headed 按需**：日常采集默认 **无头（`headless`）**；仅在调试、试跑、必须人工介入或后台强依赖可见 UI 时改为 **有头（`headed`）**。

## 6. 安全、合规与隐私（立项级要求）

1. **授权与用途**：仅处理企业有权访问的后台数据；遵守平台服务条款与内部数据分级制度。
2. **个人信息**：对手机号等字段执行脱敏/假名化策略；明确**谁可在何种系统**查看何种粒度。
3. **传输与存储**：TLS；服务端密钥与审计日志；客户端本地敏感缓存加密（若保留）。
4. **多租户隔离**：租户 ID 贯穿绑定、任务、上传；服务端强校验；数据库层可考虑 RLS（视最终模型而定）。
5. **执行落点审计**：记录任务由哪台 `device_id` 执行、哪一版规则、是否含 Excel 批次；禁止服务端代理解析未脱敏 Excel（除非走已评审的加密暂存方案）。

### 6.1 用户、身份与登录（已确认方向 · 与后续迭代）

本小节将 **本系统 Web/API 用户与登录** 与 **抖音/企业号后台的登录态（Playwright `storageState`）** 严格区分，后者见第 4.2 节。

**1）角色（首版纳入词表，按 RBAC 配置）**

| 角色 | 说明 |
|------|------|
| 平台/系统管理员 | 多租户、全局策略、跨租户审计（若需要） |
| 租户管理员 | 本租户内用户、部门、设备与数据策略 |
| 部门/团队管理员 | 子组织范围内的用户与数据范围（可裁剪实现顺序） |
| 操作员（跑客户端的人） | 使用绑定客户端、关注任务与失败回执、触发本机可执行操作 |
| 只读/分析 | 以 **「数据大盘」** 等**只读**能力为主；**不**改规则/不控设备（权限可配置是否首版就上线，建议与「分析角色」同批建模） |

**2）Web 认证（首版基线 + 可选项）**

- **首版主路径**：**账号 + 密码** 登录。  
- **首版可选项（产品开关）**：**邮箱 + SMTP** 能力，用于**自助注册/邮箱登录/忘记密码/邮箱验证**（**非强制**开给所有租户，避免开放注册滥用；**防机器人与频控** 在实现设计中写明）。手机验证码、企业 **SSO（OIDC/SAML/企业微信/飞书等）** 作为**后续迭代**，不阻塞首版闭环。  
- **会话**：**HTTPS**；**HttpOnly + Secure** Cookie 或 **Access + Refresh Token**；**不在 URL 长期带明文凭据**。

**3）多租户（已确认）**  
一人可加入**多个企业（租户）**：必须 **显式选择「当前租户」**（子域/路径/Header 等之一），**请求全链路**携带 `tenant_id` 并由**服务端**校验，与 JWT/Session 中主体一致，**防串租户**；禁止仅靠前端切换 Tab 假装隔离。

**4）权限与数据范围（已确认）**

- **RBAC** 控制：可见**菜单**、**可操作的设备/自动化规则/任务**（增删改查与下发范围分开定义均可）。  
- 数据层：**行级**（如部门/账户/时间范围）与**列级**（敏感指标）与 **「数据大盘」**、导出策略一致，与脱敏第 2 条建设目标对齐。  

**5）单用户与多台「绑定设备」（已确认，替代原“一对一”纠结）**  

- 同一**平台用户**下允许 **绑定多台** `device_id`（如办公机 + 笔记本）；**每台**设备有独立**设备凭证**。  
- **下发任务**时须**显式指定**目标 `device_id`（或经策略解析为**默认设备/设备组**）；用户仅能对 **RBAC 已授权**的设备发起/接收任务。  
- 落库：**谁**、在**何租户**下、于何时完成绑定与授权；**解绑**时吊销该设备 token 并记审计。  

**6）Electron 客户端**  

- 日常以 **设备凭证** 走 WSS/上传，**不**以「每次手输与 Web 相同的人密码」为默认体验；**首次绑定/解绑**可要求 Web 已登录后二次确认。从客户端**打开 Web** 时，尽量复用**系统浏览器**中的本系统会话（**首版**以账密/邮箱态为准；**SSO 上线后**再对齐 IdP 单点表现）。

**7）安全与审计**  

- 登录、改权、解绑、规则发布、任务下发明细 **审计**；**密码/哈希** 不入日志。  

**8）与「待决策清单」的衔接**  
原待决第 **8、12** 条已按本节收敛，见下节**待决策**中的「已决 / 续待决」说明。

### 6.2 Web「员工账号管理」菜单：企业员工号与「员工个人号授权」（已确认方向）

**菜单中文名**  
Web 控制台侧栏/导航中固定为 **「员工账号管理」**（与「数据大盘」「自动化规则」「线索管理」「视频管理」「推荐视频」并列，**全站统一**）。

**业务背景（对齐抖音企业号后台常见结构）**  
在 [抖音企业号商家管理后台](https://leads.cluerich.com/) 的矩阵营销等模块中，存在 **「企业员工号」** 与 **「员工个人号授权」** 两类入口（双 Tab/双列表）：前者侧重**企业侧开通或分配**的账号体系，后者侧重**员工个人抖音号**经企业授权后纳入统一经营与数据采集范围。本系统在 **「员工账号管理」** 菜单内提供**对等的分轨管理**，避免混在一个列表里导致权限、过期与撤销口径不清。

**与「企业号线索版」主体的层级关系（已定）**  
矩阵内的每一条 **抖音业务账号**（`account_id`）在业务上均隶属于 **同一企业号线索版/商家后台下的「企业（商家）主体」**（即登录 `leads.cluerich.com` 时所代表的企业维度，而非本系统的 `tenant_id`）。本系统须在主数据中保存 **抖音侧该主体的固定标识**（字段 **`dy_leads_enterprise_id`**，命名与实现映射见 **`docs/数据字典-员工账号.md`**），以便：与后台授权与可见范围对齐、多 `account_id` 归并到同一主体下做筛选与审计、与 **视频实体**（见 **`docs/数据字典-视频.md`**）及线索数据在同一主体边界内关联。

**Web 端产品形态（菜单内子视图）**

- **「员工账号管理」**下设两个子视图（子 Tab 文案可与抖音后台对齐，**侧栏父级名称**仍为「员工账号管理」）：  
  - **企业员工号**：企业号维度列表；字段含企业侧标识、部门、岗位、状态等（以详细设计为准）。  
  - **员工个人号授权**：个人抖音号授权列表；参考后台常见列：**抖音号/昵称**、**备注**、**所在部门**、**岗位**、**授权时间**、**过期时间**、**授权状态**、**修改/撤销** 等。  
- **操作**：支持 **添加/修改/撤销** 授权（RBAC 控制谁可改）；**导出列表**（若开放，需审计与水印策略）。  
- **与采集任务的关系**：任务或规则运行时选择的 **`account_id`** 必须能**唯一映射**到上述两类之一（**已定**：在抖音平台下 **`account_id` = 抖音侧固定不可变的唯一标识——产品统称「抖音ID」**；**不可**用昵称、短「抖音号」等可变展示字段充当 `account_id`）。客户端 `storageState` 与**具体业务账号**的对应关系在绑定/配置流程中写清，**禁止**同一任务在不知情下串号。

**数据与权限**

- 两类账号均挂在 **当前租户** 下，继承 **部门 / 行级** 数据范围；**撤销/过期** 后对应 `account_id` **不可再被选为任务目标**（或任务失败并提示续授权）。  
- **个人号授权**涉及员工个资与平台授权记录，**审计**要求高于纯企业号列表（谁在何时撤销、导出）。

**与 §6.1 的关系**  

- §6.1 的 **「平台用户」** = 登录你们控制台的账号；§6.2 的 **「业务账号」** = 在抖音侧经营企业内容的**企业号/已授权个人号**，二者不可混表。

**实现分期（可写入迭代）**  

- **首版**：可先支持一类 + 预留另一类 schema；或两轨同时只做**列表与状态维护 + 与任务下拉联动**（不在首版做「在控制台内完成抖音 OAuth 全流程」除非已具备资质与接口）。**续待决**：与抖音开放平台/后台 API **自动同步**员工列表，还是 **运营手工维护 + 客户端登录态校验** 为主。

#### 6.2.1 业务账号主键与多平台字段命名（已定）

- **`account_id`（业务账号主键，跨菜单引用）**：在 **`platform = douyin`** 时，**等于抖音侧官方固定、不可随昵称/资料变更而改写的唯一 ID**（产品口径统称 **「抖音ID」**）。任务、规则、线索、视频、推荐分等 **FK 一律使用 `account_id`**（及 `tenant_id`），保证与客户端 `storageState`、上报数据可对账。对接工程须将开放平台/矩阵后台返回的**具体字段名**与本口径写进 **`docs/数据字典-员工账号.md`** 的「实现映射」节，避免与 **短抖音号、sec_uid、昵称** 混用。  
- **抖音专有列名前缀 `dy_`**：凡表示**取自抖音或仅对抖音有意义**的库表列（如主页 URL、平台侧累计指标快照列等），**PostgreSQL 物理列名**建议使用 **`dy_` 前缀**，便于后续接入 **小红书**（建议 `xhs_`）、其它平台时同表或分表扩展。  
- **不属于 `dy_` 的列**：`tenant_id`、本系统 **`id`（内部 UUID，可选）**、**`platform` 枚举**、**`owner_user_id`（负责人 → 平台用户）**、部门外键、运营状态枚举等，属**租户/组织/本系统语义**，不按平台加前缀。  
- **指标类数据**：粉丝、赞藏评转、投放金额等**随时间变化**的字段，**主数据行**仅可保留「最近一次同步」作展示缓存；**趋势与对账**以 **`account_id` + 统计日期（或同步批次）** 的明细/快照表为准（字段级清单见 **`docs/数据字典-员工账号.md`**）。  
- **企业号线索版主体**：每条 **`biz_account`** 须带 **`dy_leads_enterprise_id`**，表达「该业务账号挂在哪一个抖音企业号线索版主体下」；**视频实体**、任务回传、线索入库在首版即应能按 **`tenant_id` + `dy_leads_enterprise_id`（及 `account_id`）** 校验归属，避免跨主体串数（详见 **`docs/数据字典-员工账号.md`**、**`docs/数据字典-视频.md`**）。

## 10. 验收标准（草案）

1. 指定试点租户下，**日级线索任务**成功率不低于约定阈值（待填，如 ≥95%）。  
2. 上传数据在 PG 中可按 **租户/部门/日期** 查询，且与客户端本地对账样本一致（在脱敏规则下可比对）。  
3. 低于最低版本的客户端**无法**执行任务或上传。  
4. BI 使用只读账号，**默认不可见**未授权敏感列（若仍存在脱敏后仍敏感字段，需单独授权模型）。  
5. Web 端具备**自动化规则**的维护、发布及向指定设备/租户**下发**能力；试点设备可仅通过更新规则（在兼容范围内）调整采集日期策略与 Tab 行为而**无需全员重装客户端**。  
6. **「数据大盘」**菜单可按 **账户 + 日期** 展示线索与短视频等核心指标，数据来源为 PG；**验证**：在绑定客户端离线时，Web 发起的含 Excel/抓取任务**不会**在服务端完成解析（以审计与网络抓包/代码评审佐证）。  
7. **「线索管理」**可按 **员工 + 时间 + 抖音账户** 筛选并展示列表与概览 KPI，数据与 RBAC 范围一致，且与 **§6.2** 账号主数据、`account_id` 联动无串数。  
8. **「视频管理」**：单 **`account_id`** 下列出全部视频；在 RBAC 范围内 **多账户聚合** 列表正确；**播放量降序**、**发布时间降序** 等排序结果与 PG 数据一致；导出（若启用）有审计记录。  
9. **「推荐视频」**：榜单与 **「视频管理」** 同一视频主键联动无误；**系统推荐** 排序与文档化 **默认公式**（含赞/评/藏/转）一致且带 **公式版本**；RBAC 范围与 §4.5 一致；Dou+ 相关能力未宣称首发即 API 闭环的，不在本项验收范围内。

5. BI 工具选型与是否上 RLS。  
6. 采集范围优先级：高潜用户/已留资/视频数据等的迭代顺序。  
7. 自动化规则采用 **JSON / DSL** 还是低代码编排器；规则是否允许包含任意脚本（一般**禁止**或仅允许受控沙箱，安全评审后定稿）。  
8. ~~**Web 用户与绑定客户端的映射**~~ **已决（首版）**：**单用户可绑定多台设备**、可**按设备**授权是否可接任务；任务须**显式/策略**指向 `device_id`。**续待决**：**按业务账户强绑**某台设备、默认设备/设备组、离线任务排队与通知。  
9. **Web 触发 Excel 导入**的传输形态：默认「客户端本地选文件」是否满足业务；若必须浏览器选文件，是否采用端到端加密暂存及 TTL（需安全评审）。  
10. **规则创建主路径**（见第 4.1.1 节）：以 **官方模板 + 参数化** 为主，还是以 **可视化编排 / Codegen 导入** 为主；**试跑与 Trace** 是否允许上传云端及脱敏策略。  
11. **正式支持的系统矩阵**：Windows 最低版本（如是否仍支持 Win10/具体构建）、macOS 最低大版本、是否发 Linux/ARM 版；与 Electron 升级锁定的**兼容性承诺周期**。  
12. ~~**Web 登录**~~ **已决（首版）**：**账号密码** 为主，**可选** 启用 **邮箱 + SMTP** 注册/登录/验证/找回；**不**以 SSO 为首发阻塞项。**续待决**：**SSO 排期**与 IdP 优先序（企业微信/飞书/Entra 等），及是否**强制**关闭公网自注册。  
13. **设备凭证生命周期**：`device` token 刷新方式、解绑后失效策略、是否对 WSS/上传分端点限流与吊销列表。  
14. **员工账号与抖音侧同步**：员工列表以 **OpenAPI/后台同步** 为主还是以 **手工维护 + 客户端校验登录态** 为主；个人号授权是否在首版闭环内完成全流程。  
15. **推荐分公式**：首版是否仅 **全局默认公式**；何时开放 **租户自定义权重**；Dou+ **批量投放** 是否纳入一年路线图及法务评估节点。

## 12. 附录：名词对照

- **逻辑版本漂移**：多台电脑安装的客户端**程序版本/规则版本**不一致，导致合并、解析、脱敏口径不一致；与「每个员工管理的后台账号不同」不是同一概念。  
- **脱敏上云**：仅将经处理的数据同步至云端，降低全员分析场景的隐私暴露面。  
- **自动化规则**：Web 侧栏菜单中文名固定为「自动化规则」；描述「在已登录后台中如何操作与抽取数据」的可下发配置（含路径、筛选、Tab、分页等）；由该菜单维护并同步至客户端执行；与**客户端程序版本**通过 schema/兼容字段协同。  
- **绑定客户端执行**：敏感数据处理（抓取原文路径、Excel 解析、合并、脱敏前步骤）仅在用户/组织绑定的 Electron 客户端上运行；Web 与云端负责编排、存储脱敏结果与大盘展示。  
- **数据大盘**：Web 侧栏菜单中文名固定为「数据大盘」；页内只读经营分析，能力可对齐后台「数据分析」；数据来自 PostgreSQL，不替代本机 Playwright 执行环境。  
- **员工账号管理**：Web 侧栏菜单中文名固定为「员工账号管理」；菜单内分 **企业员工号** / **员工个人号授权** 等子视图，维护与本租户采集相关的抖音业务账号主数据；每条业务账号须关联 **企业号线索版主体**（**`dy_leads_enterprise_id`**）；**`account_id` / `dy_` 命名与字段级清单**见 **§6.2、§6.2.1** 与 **`docs/数据字典-员工账号.md`**。  
- **客户端使用路径**：客户必装 Electron 以完成绑定与本地执行；客户端通过引导、托盘状态与「打开 Web」降低使用门槛；**「自动化规则」在客户端以只读+跳转 Web 编辑为主**，避免双端重复编辑器。  
- **规则解释器（Rule Runner）**：运行在客户端子进程内，将下发的声明式规则（JSON/受控 DSL）转换为 **Node/TypeScript** Playwright API 调用及可选网络监听；与 **规则 schema 版本** 绑定；**并发、BrowserContext 复用、Trace 默认关、headed 按需** 见 **§5.3**。  
- **平台用户与登录**：指本系统 Web/ API 的账号、会话与 RBAC；与 **抖音企业号后台** 的浏览器登录（`storageState`）是两条独立链路。  
- **设备凭证**：绑定成功后颁发给 Electron 客户端的、用于 WSS/上传的令牌及刷新机制，不等同于操作员在 Web 上的个人密码。  
- **当前租户**：多租户用户在一次会话中**显式**选中的 `tenant_id`，全链路必携参与校验。  
- **企业员工号**：企业侧开通或分配、纳入统一经营/采集范围的企业号类账号（与后台「企业员工号」语义对齐，具体字段以详细设计为准）。  
- **员工个人号授权**：员工个人抖音号经企业授权后纳入矩阵/采集范围；含授权/过期/撤销等生命周期，与后台「员工个人号授权」语义对齐。  
- **线索管理**：Web 侧栏菜单中文名固定为「线索管理」；对线索的**列表与概览**能力，支持按员工、时间、抖音账户等筛选；数据来自本系统 PG，与「数据大盘」互补（大盘偏指标分析，线索管理偏列表运营）；**线索实体**见 **§4.4 与数据模型** 及 **`docs/数据字典-线索.md`**。  
- **视频管理**：Web 侧栏菜单中文名固定为「视频管理」；对绑定关联的抖音业务账户下的**视频清单**做查询、筛选与排序（如播放量、发布时间）；支持单账户与权限范围内多账户视图；数据来自 PG；**每条视频**为独立**视频实体**（见 §4.5、**`docs/数据字典-视频.md`**）。  
- **企业号线索版主体**：抖音矩阵中各业务账号所隶属的、在 **[企业号线索版后台](https://leads.cluerich.com/)** 下的企业/商家维度标识；本系统以 **`dy_leads_enterprise_id`** 与 **`account_id`** 关联存储（见 §6.2、**`docs/数据字典-员工账号.md`**）。  
- **推荐视频**：Web 侧栏**独立顶层**菜单中文名固定为「推荐视频」；在权限范围内聚合多账户视频，基于赞/评/藏/转等 **综合公式** 评选优质内容并辅助投放决策；与「视频管理」**同源数据、联动跳转**；Dou+ API 对接为可选后续能力。  
- **投放管理**：Web 侧栏**一级**展示名 **「投放管理」**；承载 **A 粒度**、按 **视频 + 投放矩阵号** 的人填投放/投前与对账，业务表、边界与**路由**见 [**`数据字典-视频投放-示意.md` §6.1**](数据字典-视频投放-示意.md)（`ad-placements`），与**账户/BI 总投放**（B 粒度）区分。  
- **侧栏菜单中文名（已全部冻结）**：以下**九项**为 Web 控制台侧栏/导航的正式展示名，开发与路由须一致，不随抖音后台子栏目名称替换；**自上而下顺序**以 **§3.3.2** 为准：**「数据大盘」**、**「员工账号管理」**、**「自动化规则」**、**「线索管理」**、**「视频管理」**、**「推荐视频」**、**「投放管理」**、**「设备绑定」**、**「系统设置」**。  
- **设备绑定**：Web 侧栏一级菜单中文名固定为「设备绑定」；承载绑定码、设备列表、`device_id`、在线/WSS 摘要、解绑与审计等；**不含**任务编排主入口（见「系统设置」）。  
- **系统设置**：Web 侧栏一级菜单中文名固定为「系统设置」；承载组织与成员、平台用户与 RBAC、任务中心等；**不含**设备列表主流程（见「设备绑定」）。  
- **信息架构（IA）**：见 **§3.3**（一级侧栏顺序、二级 Tab、「设备绑定 / 系统设置」边界、路由与深链建议）。  
- **`account_id`（业务账号）**：全站引用抖音**业务账号**时的主键；**已定**在抖音平台下 **`account_id` = 抖音侧固定不可变唯一 ID（「抖音ID」）**；与 **平台用户**（登录控制台）区分。详见 **§6.2.1** 与 **`docs/数据字典-员工账号.md`**。  
- **`dy_` 字段前缀**：PostgreSQL 中**抖音专有或可溯源抖音**的列名前缀，与 **`xhs_` 等**并列，支撑多平台扩展；约定见 **§6.2.1** 与 **`docs/数据字典-员工账号.md`**。  
- **脱敏白名单（上云字段）**：见 **`docs/脱敏白名单-上云字段.md`**（与 §4.2 配套；**Playwright 定稿后回填**解析来源与 L0–L3 定级）。  
- **任务与设备（控制面数据模型）**：见 **`docs/数据字典-任务与设备.md`**（`biz_device` / `biz_task` / `biz_task_run`；**设备 WSS 上下行消息契约见该文档 §8**）。
