## 1. 文档范围

- **菜单**：Web「**员工账号管理**」——子 Tab **企业员工号**、**员工个人号授权**。  
- **对象**：**抖音侧业务账号**（企业号体系 / 已授权个人号），**不是**登录控制台的 **平台用户**（后者见「系统设置」组织与成员 / RBAC）。  
- **不包含**：视频逐条列表（见 **`数据字典-视频.md`** 之 **`biz_video`**）、线索用户逐条（见 **`数据字典-线索.md`** 之 **`biz_lead`**）；本表仅定义**账号主数据**及与账号**一对一或低频更新**的抖音展示字段；**时序指标**见第 7 节。

**与「线索 / 来源」的联动（产品 2026-04-25）**  
- **`biz_account` 的刷新**：**主路径** 为户在 Web 中 **【手动】点「更新」/「同步」**（**一次** 拉 P2 企业员工号 + P3 个人号授权 或等价 BFF 流程）写入/合并本表。  
- **按需自动**：在同步或展示**线索**时，若该行的 **「来源:」** 展示名 在 **`biz_account` 中尚不存在** → 系统**自动** 再执行**一次** 上列拉取，再**按** `dy_display_name` 等与 **来源** 对 **`account_id`**。  
- **对不上时**：**自动**拉完后 **仍** 无匹配 → **不静默失败**：按 **`数据字典-线索.md` §2 原则 6** **提示用户检查** 后台/命名/是否未入矩阵，并引导至**本菜单** 人工核对。  
- 技术对账、URL 与 JSONPath 仍见 **`docs/Playwright字段定位清单.md` §1 P2/P3、§3、§0.2 T07**（可后续补全）。

## 2. 全局约定

### 2.1 `platform`（平台枚举）

| 取值 | 说明 |
|------|------|
| `douyin` | 抖音企业号矩阵 / 线索后台体系（首版） |
| `xiaohongshu` | 小红书（预留，字段建议前缀 `xhs_`） |
| … | 其它平台按同样规则增加枚举与前缀 |

### 2.2 `account_id`（业务账号主键）

- **语义**：跨任务、规则、线索、视频、报表引用的**业务账号唯一键**。  
- **已定（抖音）**：当 `platform = douyin` 时，**`account_id` = 抖音侧「抖音ID」——官方固定、不因昵称/主页文案修改而改变的唯一标识**。  
- **禁止**：将**短抖音号**、**昵称**、**仅展示用主页短链**、或其它**可变更**字符串作为 `account_id`。  
- **库表约束**：建议 **`(tenant_id, platform, account_id)` 唯一**；若使用本系统 **`id`（UUID）** 作 ORM 主键，仍须在业务层与 API 中保留 **`account_id` 可查可筛**。

### 2.3 `dy_` 前缀（抖音专有列）

- **规则**：表示**数据源自抖音或语义仅对抖音成立**的 PostgreSQL 列，使用 **`dy_` 前缀**。  
- **反例（不加 `dy_`）**：`tenant_id`、`id`、`platform`、`account_id`、`owner_user_id`、`dept_id`、`ops_status`、`account_kind`、`created_at` / `updated_at` 等本系统或跨平台通用字段。  
- **小红书**：新平台专有列使用 **`xhs_`**（示例：`xhs_user_id`），与 `dy_` 对称；通用指标可抽象为中性列名 + `platform`，或由分表承载（详细设计时二选一）。

### 2.4 `account_kind`（本菜单内分轨）

| 取值 | 对应 Tab | 说明 |
|------|----------|------|
| `enterprise_staff` | 企业员工号 | 企业侧开通/分配的企业号体系账号 |
| `personal_authorized` | 员工个人号授权 | 员工个人抖音号经企业授权纳入采集范围 |

### 2.5 企业号线索版主体（与抖音业务账号的隶属关系）

- **业务含义**：在 **[抖音企业号线索版 / 商家管理后台](https://leads.cluerich.com/)** 中，矩阵下的多个 **抖音业务账号**（`account_id`）通常挂在**同一企业（商家）主体**下运营；该主体与你们本系统的 **`tenant_id` 不必一一相等**（一个 SaaS 租户可管理多个抖音主体，或反之，以商务与对接为准），但**在抖音侧必须有稳定 ID 可对账**。  
- **字段**：本系统用 **`dy_leads_enterprise_id`**（`dy_` 前缀）存「**当前这条 `biz_account` 所隶属的企业号线索版侧主体**」的**固定标识**；展示名可用 **`dy_leads_enterprise_name`**（可变，仅展示）。  
- **约束（建议）**：`(tenant_id, platform, dy_leads_enterprise_id, account_id)` 在矩阵授权边界内合法；**视频实体**、任务回传、线索入库须携带或与该主体一致，防止跨主体串数（见 **`数据字典-视频.md`** §2、§4）。

## 3. 逻辑实体建议（表级草案）

首版可 **单表 `biz_account`**（或 `tenant_biz_account`）承载两轨，用 `account_kind` 区分；字段按「必填 / 仅个人轨」在下列中标注。若两轨生命周期差异大，再拆子表（M0 评审定）。

## 4. 字段表：主数据（`biz_account` 示意）

以下列名面向 **PostgreSQL**；类型为示意，以实现为准。

### 4.1 全轨通用

| 物理列名 | 类型（示意） | 必填 | 说明 |
|----------|--------------|------|------|
| `id` | `uuid` | 是 | 本系统行主键（可选，亦可仅用复合键） |
| `tenant_id` | `uuid` | 是 | 租户 |
| `platform` | `text` | 是 | 见 §2.1，首版多为 `douyin` |
| `account_id` | `text` | 是 | **抖音固定 ID**，见 §2.2 |
| `account_kind` | `text` | 是 | `enterprise_staff` \| `personal_authorized` |
| `dy_leads_enterprise_id` | `text` | 条件 | **企业号线索版主体**固定 ID；`platform=douyin` 时**建议必填**，与矩阵/后台授权范围对齐 |
| `dy_leads_enterprise_name` | `text` | 否 | 主体展示名（可变，仅 UI） |
| `ops_status` | `text` | 否 | 运营状态，例：`running` 运营中、`paused` 暂停（枚举在实现中冻结） |
| `owner_user_id` | `uuid` | 否 | **负责人** → 平台用户（本系统）；**不加** `dy_` |
| `dept_id` | `uuid` | 否 | 所在部门（与组织架构一致） |
| `position` | `text` | 否 | 岗位/职务描述 |
| `created_at` | `timestamptz` | 是 | 写入时间 |
| `updated_at` | `timestamptz` | 是 | 最近更新 |

### 4.2 抖音展示与对接（`dy_`）

| 物理列名 | 类型（示意） | 必填 | 说明 |
|----------|--------------|------|------|
| `dy_display_name` | `text` | 否 | 昵称/展示名，**可变**，需允许同步更新 |
| `dy_unique_id` | `text` | 否 | 短「抖音号」等**可变**展示标识；**不等于** `account_id` |
| `dy_profile_url` | `text` | 否 | 个人主页链接（如短链解析结果或规范 URL） |
| `dy_positioning` | `text` | 否 | 平台定位/赛道描述（运营维护或同步） |
| `dy_avatar_url` | `text` | 否 | 头像 URL（若上云需合规与 TTL 策略） |

### 4.3 仅「员工个人号授权」轨常用

| 物理列名 | 类型（示意） | 必填 | 说明 |
|----------|--------------|------|------|
| `remark` | `text` | 否 | 备注 |
| `authorized_at` | `timestamptz` | 条件 | 授权生效时间 |
| `expires_at` | `timestamptz` | 否 | 过期时间，空表示长期或未填 |
| `auth_status` | `text` | 是 | 例：`pending` / `active` / `expired` / `revoked` |
| `revoked_at` | `timestamptz` | 否 | 撤销时间 |
| `revoked_by_user_id` | `uuid` | 否 | 撤销操作人（平台用户） |

**企业员工号**轨可将 `auth_status` 固定为 `active` 或单独枚举，与矩阵后台状态对齐（详细设计定稿）。

## 7. 指标类（不入主数据「真理源」或仅存展示缓存）

以下对应 Notion 中的粉丝、内容量、赞藏评转、**账户级**投放/经营汇总等，**建议独立快照表**（示例名 **`biz_account_daily_stat`** 或 **`biz_account_metric_snapshot`**）：

- **与「按视频、人填的投放/记账」的边界**：**§7 表**中的 **`dy_ad_*`** 等列是 **B** 粒度 —— **单账户、按日/按批** 的**总** 粉丝/互动/**总投放** 等，**可** 来自**广告平台/接口**（若以后接），见 [**`数据字典-视频投放-示意.md` §0 粒度 B**](数据字典-视频投放-示意.md)。**单条视频、一轮/一次** 的投放与「**今日消耗/投前**」、状态/再投 等 属于 **A** 粒度，落在示意表 **`biz_ad_placement`**；**不** 直接写入 **`biz_account`** 主数据行 或 本 节 行 **除非** 有**日汇总/派生** 任务 将 按视频 数据 汇总 成 账户 日 记。详见 **`数据字典-视频投放-示意.md`** 全文。

| 物理列名（示意） | 说明 |
|------------------|------|
| `tenant_id` | 租户 |
| `platform` | 平台 |
| `account_id` | FK 至主数据 |
| `stat_date` 或 `synced_at` | 统计日或同步批次 |
| `dy_follower_count` | 粉丝数 |
| `dy_video_count` | 内容条数（视频数，可与视频表 count 对账） |
| `dy_total_likes` | 累计点赞 |
| `dy_total_favorites` | 累计收藏 |
| `dy_total_comments` | 累计评论 |
| `dy_total_shares` | 累计分享/转发 |
| `dy_ad_spend_total` | **B**：账户级总投放等（**若** 来源为 广告/接口）；**A** 级 人填 按视频 见 `biz_ad_placement` |
| `dy_ad_new_followers` | 总进粉（投放口径） |
| `dy_ad_campaign_count` | 投放次数（账户级） |

主数据表上是否冗余 **`last_metric_synced_at` + 少量 `dy_*_latest`** 由性能与产品决定，**不得**替代快照表做趋势分析。

## 8. 关联关系（摘要）

- **任务 / 自动化规则**：入参带 `tenant_id` + `account_id`（+ `device_id`）；若任务范围按抖音主体收口，可增加 **`dy_leads_enterprise_id`** 校验；任务与设备表结构见 **`数据字典-任务与设备.md`**。  
- **线索 / 视频 / 推荐**：**线索**为独立实体 **`biz_lead`**（**`数据字典-线索.md`**）；**视频**为 **`biz_video`**（**`数据字典-视频.md`**）；均须带 `tenant_id`、`dy_leads_enterprise_id`、`account_id`（及各自平台主键 **`dy_lead_wlz_id` / `dy_lead_ylz_id`** 与 `dy_video_id`）。
