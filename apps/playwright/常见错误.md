# Playwright 常见错误与规约

本文档用于沉淀 Playwright 自动化规则在「控制台下发 / 客户端试跑 / Runner 执行」链路中的常见问题与标准修复，避免重复踩坑。

## 1. `goto.path` 缺少 `consoleBase`

- **现象**：
  - `VALIDATION_FAILED: goto.path 需配合 consoleBase 参数才能拼出绝对地址`
- **根因**：
  - 规则只写了 `goto.path`，但当前执行链路未传 `console_base`，无法拼绝对 URL。
  - 常见于：控制台只上传单个 `rule.json`，未走文件规则 `meta.console_base` 兜底。
- **标准修复**：
  - 规则默认使用 `goto.url`（绝对地址），不要依赖 `path`。
  - 仅在确认执行链路稳定注入 `console_base` 时才使用 `goto.path`。

## 2. `captureResponse` 抓到 `null` 或超时

- **现象**：
  - `wait response_key=...` 超时；
  - `captures.<key> = null`。
- **根因**：
  - `url_pattern` 太宽或不准，先命中非目标响应；
  - 页面未触发目标请求；
  - 等待时机不对（先 `wait` 后触发请求）。
- **标准修复**：
  - `url_pattern` 指向主列表接口关键路径；
  - 顺序固定：先 `captureResponse` -> `goto`/`click` 触发 -> `wait response_key`；
  - 必要时提高 `timeout_ms`（如 45s）。

## 3. 规则可下发但无法入库

- **现象**：
  - 规则执行成功，但数据库无新增。
- **根因**：
  - 只完成采集，没有进入入库链路；
  - `rows` 为空且无 `captures -> rows` 转换；
  - 任务缺少文件规则来源标识。
- **标准修复**：
  - 对目标规则实现 `captures -> rows` 转换；
  - 确保任务 payload 带 `rule_source=filesystem`（文件规则模式）；
  - 确认后端入库接口与目标表映射已配置。

## 4. 新规则默认设计规范（强制）

1. 导航默认 `goto.url`（绝对地址）；
2. 主数据优先 `captureResponse`，DOM 只兜底；
3. 必须有闭环步骤：`captureResponse` + `goto/click` + `wait(response_key)`；
4. 字段首版优先保留原值（避免猜枚举语义）；
5. 交付前必须完成一次试跑并保留成功日志证据。

## 5. 交付前检查清单

- [ ] 规则 JSON 单独下发可运行（不依赖外部隐式配置）。
- [ ] 试跑无 `VALIDATION_FAILED`。
- [ ] `captures` 命中主 payload（非 `null`）。
- [ ] 至少 1 条样本可映射到目标库字段。
- [ ] 入库链路验证通过（写入条数 > 0 或有明确跳过原因）。

## 6. `NAV_FAILED` / `net::ERR_CONNECTION_CLOSED`（导航被断连）

- **现象**：
  - 日志中 `event=ready` 仍成功，但某步 `goto` 报 `NAV_FAILED`；
  - Playwright 原文常含 `page.goto: net::ERR_CONNECTION_CLOSED` 或 `ERR_CONNECTION_RESET` 等。
- **说明**：
  - **不是**「Chromium 未安装」类故障：子进程能输出 `ready` 说明持久化指纹浏览器已启动。
  - 前几步 `captureResponse` 若极快 `ok`，通常只是**注册监听**，不代表已能连上外站。
  - 断连多发生在 **TLS/TCP 尚未完成** 时：本机/企业网络、出口拥塞、对端或 CDN 主动断连、部分地区线路敏感等。
- **客户侧一线排查**：
  1. 用系统 Chrome/Edge **打开与日志中相同的完整 URL**，是否稳定可开。
  2. 换网络或时段（如手机热点、非公司网、非高峰）。
  3. 在支持的前提下用**有头**试跑/任务（`ZHIZHU_TASK_RULE_HEADED` 等）对比是否仅 headless 复现。
  4. 排查企业 HTTPS 审查、代理、杀软流量扫描（按客户规范加白或短时对比）。
- **规则侧可选**：在对应 `goto` 步骤配置 `nav_retry_count`（额外重试次数，0–5）与 `nav_retry_backoff_ms`（重试间隔 ms，200–10000）；Runner 仅对若干瞬时 `net::` 错误自动重试。
